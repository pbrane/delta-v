## PR1 lessons already baked into PR2's plan (verify, don't reinvent)

PR1's Phase 4 surfaced three real architectural integration bugs that unit tests + 2-stage review didn't catch. **PR2's plan addresses each upfront** — verify each is in the executed code rather than rediscovering at integration:

1. **Envoy route gap** → Task 9 explicitly adds the `/org.deltav.minion.grpc.v1.TwinChannelService/` prefix match. If skipped, Minion gets `UNIMPLEMENTED` on first stream open. Verify Task 9's `envoy.yaml` diff and the Envoy config-validate step before moving past Phase 2.

2. **Missing `@EnableKafka`** → Task 8's `TwinChannelConfiguration` reuses PR1's existing `@EnableKafka` from `RpcChannelConfiguration` (same Spring context). If `@KafkaListener` doesn't get registered, the dispatcher's listener never receives messages — silent failure, not visible in unit tests. Verify the Kafka container factory's listener startup logs at gateway boot.

3. **Wire-format translator** → Tasks 4 (state cache) and 8 (dispatcher) translate horizon's `TwinResponseProto` ↔ rc2's `TwinUpdate` proto. Plan Task 8's `handleHorizonUpdate` is the load-bearing piece; without it, dispatcher would silently drop or corrupt every update. Mirror the verification PR1 used: log inspection at the gateway should show `Twin SUBSCRIBE` followed by snapshot-or-patch broadcasts with non-empty `consumer_key` and `location`.

## Specific PR2 nuances vs PR1

- **Twin is broadcast, not load-balanced.** PR1's `MinionStreamPool` does round-robin per RPC. PR2's `MinionTwinSubscriberRegistry` (Task 6) is a per-(key, location) **set** — every update goes to all subscribers. Different concurrency profile.
- **Gateway is stateful for Twin.** PR1's dispatcher was stateless wrt request bodies. PR2's `TwinStateCache` (Task 4) holds per-(key, location) current state + version + sessionId, recovered on cold start by `auto.offset.reset=earliest` on the Kafka consumer (Task 8.4). Multi-instance friendly because each gateway instance independently rebuilds state from Kafka.
- **JSON Patch generation.** Task 5's `TwinPatchGenerator` is a thin wrapper around Jackson `JsonDiff`, mirroring horizon's `AbstractTwinPublisher.getPatchValue()`. RFC 6902 compliance is the contract; on parse failure, return null to signal snapshot fallback.
- **Subscriber-side version-gap recovery.** Task 10's `MinionTwinStreamClient` detects non-contiguous version → drops stream → reconnects (yields fresh snapshot per Decision 2 sub-decision 2-i). Watch for infinite-loop risk: Task 10's tests verify the `sessionId` change case (publisher restart) bypasses the gap check.

- **Image rebuild discipline.** `build.sh deltav` rebuilds the 12 daemon images + minion-boot but NOT minion-gateway or envoy (PR4 fixes this).
