## Background

v1.3.0 Track 3 inverts alarm storage: Kafka becomes the source of truth and PostgreSQL becomes a materialised read-only view. Spec: [`../specs/2026-05-22-v1.3.0-track3-alarm-materializer-design.md`](../specs/2026-05-22-v1.3.0-track3-alarm-materializer-design.md) §6 (failure modes).

This tabletop walks each failure case from the spec and confirms the design handles it as documented.

**Participant setup:** [`2026-05-22-v1.3.0-track3-tabletop-runbook.md`](./2026-05-22-v1.3.0-track3-tabletop-runbook.md) — clone, build, bring up the stack on your laptop.

## Scenarios walked

| # | Scenario | Expected behaviour | Reproduction recipe | Observed |
|---|---|---|---|---|
| 1 | Kafka broker outage during steady state | Alarmd stops consuming + producing; events back up on input topic; Minions buffer | `docker compose stop kafka`; observe alarmd logs; `start kafka`; confirm pickup | _(fill in)_ |
| 2 | Alarmd cold start with broker unreachable | ReductionCache bootstrap stalls; /actuator/health/readiness stays DOWN | `down -v` then `up -d` with Kafka explicitly held back; observe alarmd readiness | _(fill in)_ |
| 3 | Materializer crash | Topic accumulates; PG falls behind; on restart bootstrap-replay catches up | `docker compose stop alarms-materializer` for ~30s while publishing alarms; restart and confirm catch-up | _(fill in)_ |
| 4 | Materializer slow (replay during steady state) | PG lag grows; lag metric increases; closes naturally | Publish a burst of synthetic alarms; observe `deltav_alarms_materializer_consumer_lag_records` metric | _(fill in)_ |
| 5 | Materializer SQL error (DB unreachable) | Consumer thread blocks retrying; back-pressure; no data loss | `docker compose stop postgres`; observe materializer back-pressure log lines; restart | _(fill in)_ |
| 6 | Alarmd crashes after producer.send but before consumer-side cache update | On restart, bootstrap-replay re-reads the record; cache consistent | Force-kill alarmd (`docker kill -s KILL`) during a publish; restart and verify ReductionCache size | _(fill in)_ |
| 7 | Tombstone published, materializer hasn't processed it yet | Eventually consistent; retention may re-emit (benign) | Manually publish a tombstone via kafka-console-producer, observe materializer DELETE catching up | _(fill in)_ |
| 8 | Tombstone races with re-publish (alarm deleted then re-created) | Last write wins; new alarmid assigned; consumers key by rk so transparent | Publish tombstone then a follow-up state record for the same key within seconds | _(fill in)_ |
| 9 | Topic compaction during alarmd restart | Compacted topic still has latest per key; cache bootstrap correct | Force compaction via `kafka-configs --alter --add-config segment.bytes=1048576,min.cleanable.dirty.ratio=0.01`; then restart alarmd | _(fill in)_ |
| 10 | Dual-write mode + materializer running concurrently | Publisher AFTER_COMMIT ordering means materializer never sees record before PG commits | Set `DELTAV_ALARMD_PERSISTENCE_MODE=dual-write`, restart alarmd, run a burst, confirm no lock contention in alarmd's transaction log | _(fill in)_ |
