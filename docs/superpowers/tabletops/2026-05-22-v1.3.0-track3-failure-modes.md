## Background

v1.3.0 Track 3 inverts alarm storage: Kafka becomes the source of truth and PostgreSQL becomes a materialised read-only view. Spec: `docs/superpowers/specs/2026-05-22-v1.3.0-track3-alarm-materializer-design.md` §6 (failure modes).

This tabletop walks each failure case from the spec and confirms the design handles it as documented.

## Scenarios walked

| # | Scenario | Expected behaviour | Observed | Status |
|---|---|---|---|---|
| 1 | Kafka broker outage during steady state | Alarmd stops consuming + producing; events back up on input topic; Minions buffer | | ☐ pass / ☐ fail |
| 2 | Alarmd cold start with broker unreachable | ReductionCache bootstrap stalls; /actuator/health/readiness stays DOWN | | ☐ pass / ☐ fail |
| 3 | Materializer crash | Topic accumulates; PG falls behind; on restart bootstrap-replay catches up | | ☐ pass / ☐ fail |
| 4 | Materializer slow (replay during steady state) | PG lag grows; lag metric increases; closes naturally | | ☐ pass / ☐ fail |
| 5 | Materializer SQL error (DB unreachable) | Consumer thread blocks retrying; back-pressure; no data loss | | ☐ pass / ☐ fail |
| 6 | Alarmd crashes after producer.send but before consumer-side cache update | On restart, bootstrap-replay re-reads the record; cache consistent | | ☐ pass / ☐ fail |
| 7 | Tombstone published, materializer hasn't processed it yet | Eventually consistent; retention may re-emit (benign) | | ☐ pass / ☐ fail |
| 8 | Tombstone races with re-publish (alarm deleted then re-created) | Last write wins; new alarmid assigned; consumers key by rk so transparent | | ☐ pass / ☐ fail |
| 9 | Topic compaction during alarmd restart | Compacted topic still has latest per key; cache bootstrap correct | | ☐ pass / ☐ fail |
| 10 | Dual-write mode + materializer running concurrently | Publisher AFTER_COMMIT ordering means materializer never sees record before PG commits | | ☐ pass / ☐ fail |

## How to exercise each scenario

(Operator notes added during the live tabletop. Some scenarios can be reproduced with `docker compose stop`/`start` patterns; others need synthetic publishes via `kafka-console-producer`.)

| # | Reproduction recipe |
|---|---|
| 1 | `docker compose stop kafka`; observe alarmd logs; restart; confirm pickup |
| 2 | Start the stack with Kafka explicitly held back; observe alarmd readiness |
| 3 | `docker compose stop alarms-materializer` for ~30s while publishing alarms; restart and confirm catch-up |
| 4 | Publish a burst of synthetic alarms; observe `deltav_alarms_materializer_consumer_lag_records` metric |
| 5 | `docker compose stop postgres`; observe materializer back-pressure log lines; restart |
| 6 | Force-kill alarmd (`docker kill -9`) during a publish; restart and verify ReductionCache size |
| 7 | Manually publish a tombstone via kafka-console-producer, observe materializer DELETE catching up |
| 8 | Publish tombstone then a follow-up state record for the same key within seconds |
| 9 | Wait for compaction (or force one via `kafka-topics --alter`), then restart alarmd |
| 10 | Configure `deltav.alarmd.persistence.mode=dual-write`, restart alarmd, run a burst, confirm no lock contention |
