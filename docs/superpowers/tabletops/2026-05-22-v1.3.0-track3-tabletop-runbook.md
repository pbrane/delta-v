# v1.3.0 Track 3 — Tabletop Participant Runbook

How to bring up the Track 3 stack on your own laptop so you can follow along
in the tabletop and run scenarios yourself.

**Worksheet:** [`2026-05-22-v1.3.0-track3-failure-modes.md`](./2026-05-22-v1.3.0-track3-failure-modes.md)
**Spec:** [`../specs/2026-05-22-v1.3.0-track3-alarm-materializer-design.md`](../specs/2026-05-22-v1.3.0-track3-alarm-materializer-design.md)

## 1. Prerequisites

You need:

- **Docker Desktop** (macOS/Windows) or **Docker Engine** (Linux), with at
  least **16 GB of memory** allocated to Docker and **30 GB of free disk**.
- **`git`** with access to `pbrane/delta-v` (any read-level access is enough).
- **`gh`** (GitHub CLI) — optional, helps with PR navigation.
- **One of:**
  - **JDK 21** + ~20 min for a one-time local build (Path A, below), or
  - Nothing extra if you take Path B (pull pre-built images from GHCR).

Verify:

```bash
docker info | grep -E "Memory|Architecture"
docker --version
git --version
java -version  2>&1 | head -1   # needs OpenJDK 21 if you're building
```

## 3. Get the images

Pick the path that suits you. **Path A is the default and most reliable.**

### Path A — Build locally (recommended)

The full build is ~15–20 minutes wall-clock the first time (Maven downloads
deps, Docker builds 28 image layers). Subsequent rebuilds use cache and are
much faster.

```bash
# Prepare your shell (auto-detected JDK is usually fine; export if needed)
export JAVA_HOME=$(/usr/libexec/java_home -v 21)    # macOS
# export JAVA_HOME=/usr/lib/jvm/java-21-openjdk     # Linux

# Build everything (Maven compile + assemble + 28 Docker images)
./opennms-container/delta-v/build.sh deltav
```

When it finishes you'll see a "Delta-V images built" summary listing all
images at the current `1.3.0-rc2` tag, including the new
`deltav/alarms-materializer:1.3.0-rc2`.

**Known foot-gun (chronic across version bumps): `build.sh deltav` does NOT
rebuild auxiliary images** (mock-snmp-agent, clickhouse, clickhouse-init,
flow-exporter, l8opensim-provisioner, sflow-exporter,
provisiond-imports-init). If `docker compose up` later fails with `pull
access denied for deltav/mock-snmp-agent`, run this one-time retag:

```bash
for img in mock-snmp-agent clickhouse clickhouse-init flow-exporter \
           l8opensim-provisioner sflow-exporter provisiond-imports-init; do
  # Find your most recent existing tag of this image and retag to 1.3.0-rc2.
  existing=$(docker images "deltav/$img" --format "{{.Tag}}" | \
             grep -v latest | grep -v 1.3.0-rc2 | head -1)
  if [ -n "$existing" ]; then
    docker tag "deltav/$img:$existing" "deltav/$img:1.3.0-rc2"
    echo "tagged $img: $existing -> 1.3.0-rc2"
  else
    echo "WARN: no existing $img image found — you'll need to build it separately"
  fi
done
```

(This is `feedback_auxiliary_image_retag_on_version_bump` in our team notes
— if `$existing` is empty for an image, you don't have a prior local build
to retag from; ask the tabletop driver to share theirs via `docker save` /
`docker load`, or set `IMAGE_PREFIX` to a registry that has them.)

### Path B — Pull from GHCR (multi-arch images, public, no auth needed)

For the Track 3 tabletop, multi-arch images (`linux/amd64` + `linux/arm64`)
have been published to `ghcr.io/pbrane/<image>:1.3.0-rc2`. Packages are
**public** so no `docker login` is needed.

```bash
# Tell compose to use GHCR images instead of local builds
export IMAGE_PREFIX=ghcr.io/pbrane

# Pull everything ahead of `up -d` so you see download progress
docker compose -f opennms-container/delta-v/docker-compose.yml --profile lite pull
```

Then proceed to §4. The same `IMAGE_PREFIX` value needs to be exported in
every shell you run `docker compose` from — easier to put it in a
session-local `.env.local` or your shell rc.

If you ever need to switch back to local-built images (Path A), simply
`unset IMAGE_PREFIX` — the compose file falls back to `deltav/<image>` and
will use whatever's in your local Docker daemon.

If the driver has not yet triggered the workflow, the GHCR tag may not
exist — you'll see `manifest unknown` errors. Ask the driver to run:

```bash
gh workflow run delta-v-build-images.yml \
  --repo pbrane/delta-v \
  --ref feat/v1.3.0-track3-materializer-design
```

then wait ~25 minutes for the multi-arch build to complete.

## 4. Bring up the stack

```bash
docker compose -f opennms-container/delta-v/docker-compose.yml --profile lite up -d
```

This brings up the `lite` profile (~12 services including alarmd,
alarms-materializer, alerts-forwarder, kafka, postgres, minion). Allow
60–90 seconds for everything to settle.

Watch progress live:

```bash
docker compose -f opennms-container/delta-v/docker-compose.yml --profile lite ps --watch
```

(Ctrl+C to stop watching — services keep running.)

---

## 5. Verify health (the "we're at the starting line" check)

Once the stack settles, every service should show `Up (healthy)`:

```bash
docker compose -f opennms-container/delta-v/docker-compose.yml --profile lite ps
```

Then exercise the three Track 3 daemons:

```bash
# alarmd — should boot in kafka-only mode and bootstrap its ReductionCache
docker logs delta-v-alarmd 2>&1 | \
  grep -E "Registered KafkaAlarmPublisher|ReductionCache bootstrap complete|Started AlarmdApplication"
docker exec delta-v-alarmd curl -fs http://localhost:8080/actuator/health/readiness

# alarms-materializer — new daemon, should consume the topic and run retention
docker logs delta-v-alarms-materializer 2>&1 | \
  grep -E "Started AlarmsMaterializerApplication|Starting alarms-materializer consumer|Retention rule"
docker exec delta-v-alarms-materializer curl -fs http://localhost:8080/actuator/health/readiness

# alerts-forwarder — should still consume the topic happily after the alarm_id label removal
docker exec delta-v-alerts-forwarder-1 curl -fs http://localhost:8080/actuator/health/readiness
```

Expected at this point:
- `Registered KafkaAlarmPublisher` log line in alarmd.
- `ReductionCache bootstrap complete (size=N)` in alarmd (N may be 0 on a
  fresh stack or N>0 if you brought up the stack against a topic that
  already has alarm-state records).
- `Started AlarmsMaterializerApplication` + `Retention rule '<id>' matched
  K alarm(s)` periodically in the materializer.
- All three readiness probes return `{"status":"UP"}`.

Inspect the PG `alarms` table directly:

```bash
docker exec -e PGPASSWORD=opennms delta-v-postgres-1 \
  psql -h localhost -U opennms -d opennms -c "SELECT count(*), max(alarmid) FROM alarms;"

docker exec -e PGPASSWORD=opennms delta-v-postgres-1 \
  psql -h localhost -U opennms -d opennms -c \
  "SELECT alarmid, reductionkey, severity, event_uei, event_severity, event_node_id
   FROM alarms ORDER BY alarmid DESC LIMIT 5;"
```

If the `event_*` columns are populated, the proto → PG projection is
working end-to-end. (After Track 3, these come from the topic, not from a
direct alarmd write.)

## 6. Useful commands for scenario reproduction

Each scenario in the [worksheet](./2026-05-22-v1.3.0-track3-failure-modes.md)
has a one-line reproduction recipe. Common building blocks:

### Stop / start a service in place (preserves volumes)

```bash
docker compose -f opennms-container/delta-v/docker-compose.yml stop <service>
docker compose -f opennms-container/delta-v/docker-compose.yml start <service>
```

Where `<service>` is one of `kafka`, `postgres`, `alarmd`,
`alarms-materializer`, `alerts-forwarder`. Use `docker compose ps` to see
the exact service names.

### Force-kill a container (simulates a crash)

```bash
docker kill -s KILL delta-v-alarmd                  # alarmd specifically
docker kill -s KILL delta-v-alarms-materializer     # materializer
docker compose -f opennms-container/delta-v/docker-compose.yml start alarmd
```

This is harsher than `stop` — no graceful shutdown, no `@PreDestroy`
callbacks. Good for "what if the JVM disappears?" scenarios.

### Watch a specific log live

```bash
docker logs -f delta-v-alarmd 2>&1 | \
  grep --line-buffered -E "ReductionCache|Registered Kafka|persistence.mode|ERROR|WARN"

docker logs -f delta-v-alarms-materializer 2>&1 | \
  grep --line-buffered -E "Retention rule|Started Alarms|Starting alarms-materializer|ERROR|WARN"
```

### Publish a raw record to the alarm-state topic

The materializer's IT exercises this via the `kafka-clients` Java API;
ad-hoc you can use `kafka-console-producer` for tombstones (null value is
trivial):

```bash
# Tombstone for a known reduction key (use one you saw via the PG query above)
echo "rk-from-the-pg-query" | \
  docker exec -i delta-v-kafka-1 kafka-console-producer \
    --bootstrap-server localhost:9092 \
    --topic deltav-alarms-state-change \
    --property "parse.key=true" \
    --property "key.separator=|" \
    --property "null.marker=DELETE"
# Now type `DELETE` and Enter; that publishes a tombstone keyed by the rk.
```

For publishing real (non-null) alarm-state records, the proto encoding is
non-trivial via shell — the tabletop driver has a small Python helper if
needed (`/tmp/build_alarm.py`).

### Inspect the topic

```bash
# Show the consumer groups (alarmd-reduction-cache-*, alarms-materializer-*, alerts-forwarder-*)
docker exec delta-v-kafka-1 kafka-consumer-groups \
  --bootstrap-server localhost:9092 --list

# Show partition end offsets (= "how many records are on the topic?")
docker exec delta-v-kafka-1 kafka-run-class kafka.tools.GetOffsetShell \
  --broker-list localhost:9092 --topic deltav-alarms-state-change

# Show a particular consumer group's lag
docker exec delta-v-kafka-1 kafka-consumer-groups \
  --bootstrap-server localhost:9092 --describe \
  --group $(docker exec delta-v-kafka-1 kafka-consumer-groups \
    --bootstrap-server localhost:9092 --list | grep alarms-materializer-)
```

### Force compaction (Scenario 9)

The topic's `cleanup.policy=compact` is set by alarmd's topic initializer,
but Kafka's default `log.segment.bytes` won't trigger compaction during a
short tabletop. To force it:

```bash
docker exec delta-v-kafka-1 kafka-configs \
  --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name deltav-alarms-state-change \
  --alter --add-config segment.bytes=1048576,min.cleanable.dirty.ratio=0.01
# Then publish a few tombstones via the recipe above, wait ~60s.
```

## 7. Teardown

```bash
docker compose -f opennms-container/delta-v/docker-compose.yml --profile lite down
```

This stops + removes containers but **preserves volumes** (so PG data,
Kafka topic state persist across `down`/`up` cycles).

To fully wipe state and start completely fresh:

```bash
docker compose -f opennms-container/delta-v/docker-compose.yml --profile lite down -v
```

The `-v` flag removes named volumes. Useful for "let me run the cold-start
scenarios from a clean slate" between tabletop scenarios.

## 9. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `pull access denied for deltav/<image>` on `up` | Auxiliary image not retagged after version bump | Run the auxiliary-retag script in §3 Path A |
| `alarmd` container stuck in `Starting` for >2 min | `ReductionCache` bootstrap can't reach Kafka | Check `docker logs delta-v-kafka-1` for broker health; the bootstrap correctly stalls until the broker is up |
| `alarms-materializer` exits with `BeanCreationException` | Schema mismatch on the `alarms` table (e.g. running against an old PG dump that lacks `event_*` columns) | `docker compose ... down -v` to wipe; let `db-init` recreate the schema fresh |
| Health probe returns 503 / connection refused | Service still starting | Wait 60s; if persistent, `docker logs <container>` for errors |
| Mac M1/M2: image pull tries amd64 | Multi-arch image manifest mismatch | The local-build path produces a native image; GHCR images are multi-arch. If pulling, confirm `docker info \| grep Architecture` matches |

## 10. Quick reference (one-screen cheat sheet)

```bash
# Set up
git checkout feat/v1.3.0-track3-materializer-design
./opennms-container/delta-v/build.sh deltav            # 15-20 min one-time

# Run
docker compose -f opennms-container/delta-v/docker-compose.yml --profile lite up -d
sleep 90
docker compose -f opennms-container/delta-v/docker-compose.yml --profile lite ps

# Verify
docker exec delta-v-alarmd curl -fs http://localhost:8080/actuator/health/readiness
docker exec delta-v-alarms-materializer curl -fs http://localhost:8080/actuator/health/readiness

# Inspect
docker exec -e PGPASSWORD=opennms delta-v-postgres-1 \
  psql -h localhost -U opennms -d opennms -c \
  "SELECT alarmid, reductionkey, severity FROM alarms ORDER BY alarmid DESC LIMIT 5;"

# Tear down
docker compose -f opennms-container/delta-v/docker-compose.yml --profile lite down
```

That's the steady state. The worksheet describes how to deviate from it.
