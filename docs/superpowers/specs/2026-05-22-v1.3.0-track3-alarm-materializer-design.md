**Status:** Design — approved in brainstorming 2026-05-22
**Release:** v1.3.0 "Alarms on Kafka"
**Parent design:** [`2026-05-17-v1.3.0-alarms-on-kafka-design.md`](./2026-05-17-v1.3.0-alarms-on-kafka-design.md)
**Sibling specs:** [`2026-05-19-v1.3.0-track2-alerts-forwarder-design.md`](./2026-05-19-v1.3.0-track2-alerts-forwarder-design.md)
**Depends on:** Tracks 1 + 2a + 2b — all merged and smoke-validated as of v1.3.0-rc2

## 1. Purpose and scope

Track 1 made alarm lifecycle observable on Kafka: alarmd dual-writes
PostgreSQL **and** publishes every state change to the compacted topic
`deltav-alarms-state-change`. Tracks 2a + 2b consumed that stream — the
alerts-forwarder forwards to Alertmanager / VictoriaMetrics. Today PostgreSQL
is authoritative; the topic is downstream and derivative.

Track 3 inverts that relationship. **Kafka becomes the source of truth**;
PostgreSQL becomes a read-only materialized projection. A new standalone
`alarms-materializer` daemon consumes `deltav-alarms-state-change` and
upserts the PG `alarms` table; it also owns retention/GC via declarative
predicate rules. Alarmd's direct PG writes are removed — alarmd reduces
events using a Kafka-bootstrapped in-memory `ReductionCache` and publishes
only to the topic.

This is the Phase 1 → Phase 2 cutover the parent v1.3 spec sketches at §3.

### What this track delivers

- A new daemon + image, `core/alarms-materializer`, that projects
  `deltav-alarms-state-change` → PG `alarms` with retention/GC.
- A behaviour change inside alarmd: PG writes removed, reduction lookup
  swapped from `AlarmDao` to a Kafka-bootstrapped `ReductionCache`.
- A feature flag, `deltav.alarmd.persistence.mode`, with values
  `kafka-only` (default at v1.3.0 GA) and `dual-write` (escape hatch
  retained for one release after GA).
- Predicate-based retention rules declared in materializer YAML.
- The "Drools (or other rules engine) as a future sidecar" path preserved
  without re-introducing the Boot 4 cycle that killed PR #258.

### Out of scope

- **Operator-facing ack/memo workflow APIs.** Delta-v has no working
  ack/memo REST surface today (the legacy `opennms-webapp-rest` was removed
  in PR #28). A workflow API is a separate piece of work. Track 3 *does*
  ensure the design accommodates one — ack/memo columns flow through the
  topic and are projected by the materializer.
- **Drools-or-other rules engine sidecar.** Architectural prep only;
  building it is a future release.
- **Alertmanager auto-silence integration** in alerts-forwarder. Ack info
  goes to Alertmanager as display-only annotations in v1.3.
- **Pre-v1.3.0 → Track 3 direct upgrade.** Documented upgrade path is
  `v1.2.x → v1.3.0-rcN dual-write → v1.3.0 GA`. Direct upgrade is not a
  Track 3 concern; the operator stages through rcN.
- **Northbounder API retirement.** That is Track 4 and lands after this.
- **Retiring the PG `alarms` table entirely** (parent spec's Phase 3).
  Deferred to v1.4+ as the parent spec already documented.

## 2. Target architecture

```
   fault events  (deltav-fault-events, Kafka)
        |
        v
   alarmd
     - consumes events, applies reduction logic
     - reads ReductionCache (in-memory, Kafka-bootstrapped) for "is rk active?"
     - publishes new state to deltav-alarms-state-change
     - NO PG writes (when persistence.mode = kafka-only)
        |
        v
   deltav-alarms-state-change   <-- SOURCE OF TRUTH
   (compacted, keyed by reduction_key, tombstones on delete)
        |
        +-----------------------------+--------------------------------+
        v                             v                                v
   alarms-materializer          alerts-forwarder                  alarmd's own
   (Track 3, new)               (Track 2b, shipped)               ReductionCache
   - bootstrap-replay raw       - bootstrap-replay raw            (live-tails
     KafkaConsumer                KafkaConsumer                    its own
   - upserts PG alarms          - forwards Alertmanager / VM       publishes)
   - emits tombstones on GC
   - owns retention rules
        |
        v
   PostgreSQL alarms table  <-- READ-ONLY materialized view
   (BSMD, future REST, future UI all read here; nobody else writes)
```

### Decisions carried in from brainstorming

- **Module shape: standalone daemon.** `core/alarms-materializer`,
  structurally cloned from `alerts-forwarder`. Own image, own
  `/actuator/prometheus`, own Spring Boot 4 startup. Aligns with delta-v's
  one-daemon-per-concern thesis ([[project_v1_2_app_observability]]).
- **Consumer mechanism: raw `KafkaConsumer` bootstrap-replay.** The parent
  spec said "Kafka Streams"; Track 2b proved raw `KafkaConsumer` is simpler
  and idempotent for a compacted topic. Same pattern here. The module does
  not depend on `spring-cloud-stream` or `kafka-streams`.
- **Write protocol: raw JDBC `INSERT … ON CONFLICT DO UPDATE`.** Not JPA.
  The materializer is a projection daemon, not a domain service; the full
  Hibernate stack would pull in startup-cycle risk and double round-trips
  under replay.
- **Reduction lookup: Kafka-bootstrapped in-memory cache in alarmd.**
  Replays compacted topic from offset 0 at startup; live-tails its own
  produces. PG drops out of alarmd entirely.
- **Failure mode: block and back-pressure.** Alarmd's input is also Kafka;
  on broker outage, alarmd stops consuming + stops producing; events stay
  on the input topic; Minions buffer upstream (existing behaviour). Startup
  bootstrap stalls on broker unreachable; `/actuator/health` stays not-ready.
- **Cutover policy: kafka-only by default at GA, dual-write as one-release
  escape hatch.**
- **Retention: declarative predicate YAML, JSON-Schema-validated.**
  `action: delete` only for v1.3. Future rules engine ships as a *sidecar*
  consuming the topic, not embedded in alarmd or the materializer.

## 3. Alarmd changes

The Track 3 work inside alarmd is concentrated. The full lifecycle —
event reduction, listener fan-out, Kafka publish — already exists from
Track 1. What changes is the persistence side: PG writes are removed and
reduction lookups move from `AlarmDao` to a `ReductionCache`.

### 3.1 `ReductionCache`

A thread-safe in-memory map keyed by `reduction_key`, holding the latest
`AlarmState` per key.

| Behaviour | Implementation |
|---|---|
| Lookup | `Optional<AlarmState> get(String reductionKey)` — read-only access during event reduction |
| Update | applied by the **consumer side** of alarmd's own Kafka publisher (alarmd reads its own writes from the topic and updates the cache) |
| Bootstrap | at startup, a raw `KafkaConsumer` on a random group id seeks to the beginning of `deltav-alarms-state-change`, replays to high-water-mark, fires `ReductionCacheReadyEvent` when caught up |
| Bound | proportional to active-alarm count (compacted topic = one record per active key); ~few KB per key; MB total |
| Tombstone | a null-value record removes the key from the cache |

This is the same pattern alerts-forwarder uses for `ActiveAlertRegistry`
and prometheus-writer uses for `NodeContextCache` — established, in
production, low risk.

### 3.2 `DeltavAlarmPersister`

A delta-v subclass of horizon's `AlarmPersisterImpl`, registered as the
`alarmPersister` bean in `AlarmdConfiguration`. Behaviour depends on the
feature flag:

| Mode | Behaviour |
|---|---|
| `kafka-only` (default at GA) | Reduction looks up the `ReductionCache`. No `AlarmDao.save()`. The existing `AlarmEntityNotifier` fan-out still fires — `KafkaAlarmPublisher` publishes the new state to the topic on AFTER_COMMIT (see §3.2.1). The cache update happens via the consumer side, not a synchronous write. |
| `dual-write` (escape hatch, one release) | Identical to Track 1's current behaviour — `AlarmPersisterImpl.persist()` writes PG via `AlarmDao` AND the notifier fans out to the publisher. PG remains authoritative; the publisher fires on AFTER_COMMIT so the materializer never races alarmd's still-open transaction (see §3.2.1). |

The mode is read at startup; runtime mode-switching is not supported (it
would require draining + restarting the consumer, with no operational
upside).

The `dual-write` escape hatch exists only to roll back from a misbehaving
materializer back to Phase 1 within one release. It is **removed in
v1.3.1** (or whichever release follows v1.3.0 GA by one cycle).

#### 3.2.1 Publisher transaction-commit ordering (Track 1 retrofit)

In **dual-write** mode the publisher MUST fire its `producer.send` only
after alarmd's JPA transaction has committed. If it fires from inside
the transaction (today's Track 1 behaviour), the materializer can read
the Kafka record before alarmd has released its row lock on `alarms`,
producing lock contention or an upsert race against an as-yet-uncommitted
row.

In **kafka-only** mode there is no PG write, but `AlarmPersisterImpl`
still opens a transactional boundary as part of its inherited semantics.
Firing on AFTER_COMMIT in this mode is equivalent to firing immediately
after `persist()` returns; using the same ordering for both modes keeps
the publisher path uniform.

The retrofit applies to `KafkaAlarmPublisher` (Track 1):

- Replace the synchronous `producer.send()` in `handleNewOrUpdatedAlarm`
  and `handleDeletedAlarm` with a registration via
  `TransactionSynchronizationManager.registerSynchronization` (or
  equivalent `@TransactionalEventListener(phase = AFTER_COMMIT,
  fallbackExecution = true)`). The actual send fires in `afterCommit()`.
- `fallbackExecution = true` ensures the listener still fires when no
  transaction is active — covers edge paths like startup tests or any
  future direct invocation.
- Send failures continue to be logged (Track 1 semantics) — no new
  retry strategy added here. The materializer's idempotent upsert means
  a duplicate send during retry is harmless.

This is a **Track 1 code change**, packaged inside Track 3's PR series,
because Track 3 cannot be safely cut over without it.

### 3.3 Per-reduction-key serialisation

Two events for the same reduction key arriving in close succession must
not race — concurrent reductions would corrupt the count and timestamp
fields. Today's PG transactional semantics provide this implicitly via
row-level locking.

After Track 3, serialisation is per-partition: events on
`deltav-fault-events` are already keyed by something node-related (verify
in plan-writing; if not, this becomes a sub-task). One consumer thread
per partition processes events in arrival order, so two events for the
same reduction key — which must hash to the same partition if the input
topic is keyed by the relevant fields — serialise naturally.

If the input topic is not keyed compatibly, a small in-process per-rk
striped lock around the reduction critical section closes the gap.
Implementation detail for the plan, not architecture.

### 3.4 Feature flag

```yaml
deltav.alarmd.persistence.mode: kafka-only    # values: kafka-only | dual-write
```

Per `feedback_no_shared_config_across_daemons`, the property is
daemon-scoped (`deltav.alarmd.*`), not shared.

Default at v1.3.0 GA: `kafka-only`. The flag exists only to roll back to
Phase 1 if the materializer misbehaves. It is removed in the next release.

### 3.5 Code that gets deleted (or short-circuited) inside alarmd

- `DeltavAlarmPersister` replaces `AlarmPersisterImpl` as the
  `alarmPersister` bean. The horizon class is **not** modified.
- When mode = `kafka-only`, the entire JPA stack (`AlarmDao`,
  `SessionFactory`, `PlatformTransactionManager`, `TransactionTemplate`)
  remains wired in the Spring context but is unused: no DAO method is
  called and no transaction is opened. Stripping it out is a follow-up
  for the release that removes the `dual-write` escape hatch — leaving
  it for v1.3.0 keeps the change minimal and the fallback symmetric.
- `CountingAlarmEntityNotifier` is unchanged — it still fans out to the
  publisher.
- `KafkaAlarmPublisher` (from Track 1) is unchanged.
- No removals from the alarmd module's pom; reactor surface unchanged.

## 4. The `alarms-materializer` daemon

A new standalone Spring Boot 4 daemon at `core/alarms-materializer`,
structurally cloned from `core/alerts-forwarder` (Track 2b).

### 4.1 Module structure

| File (under `core/alarms-materializer/`) | Responsibility |
|---|---|
| `pom.xml`, `Dockerfile`, `src/main/resources/application.yml` | module build + container + config |
| `.../materializer/AlarmsMaterializerApplication.java` | Spring Boot entry point |
| `.../config/MaterializerProperties.java` | binds `deltav.alarms-materializer.*` |
| `.../config/RetentionRulesValidator.java` | JSON-Schema-validates retention rules at startup |
| `.../consume/AlarmStateKafkaConsumer.java` | bootstrap-replay raw `KafkaConsumer` (cloned from alerts-forwarder) |
| `.../upsert/AlarmUpsertWriter.java` | composes and executes the `INSERT … ON CONFLICT … DO UPDATE` SQL |
| `.../upsert/AlarmStateProjector.java` | mapping rules — `AlarmState` proto → SQL parameter row |
| `.../delete/AlarmDeleter.java` | `DELETE FROM alarms WHERE reductionkey = ?` on tombstone consume — does not produce its own tombstone (retention engine is the only tombstone producer) |
| `.../retention/RetentionRule.java` | one validated rule |
| `.../retention/RetentionEngine.java` | scheduled task; reads PG, evaluates rules, deletes + tombstones matches |
| `.../retention/PredicateEvaluator.java` | named-field predicate evaluation; no expression engine |
| `.../metrics/MaterializerMetrics.java` | `deltav_alarms_materializer_*` Micrometer name constants |

### 4.2 Consumer

Identical pattern to alerts-forwarder's `AlarmStateKafkaConsumer`:

- Raw `KafkaConsumer` on a **random group id** (each restart replays).
- `seekToBeginning(partitions)` at startup.
- Reads to high-water-mark, then live-tails.
- Per-record handling delegates to `AlarmUpsertWriter` (non-tombstone) or
  `AlarmDeleter` (tombstone, null value).
- On sink failure (PG unreachable, SQL error), the consumer thread blocks
  retrying — natural back-pressure (no poll → broker doesn't send more).
- Idempotent by construction — `INSERT … ON CONFLICT … DO UPDATE` is
  identity if the record matches what's already there.

### 4.3 Write protocol

Raw JDBC via `JdbcTemplate`. SQL shape:

```sql
INSERT INTO alarms (
  eventuei, nodeid, ipaddr, serviceid, reductionkey, alarmtype,
  counter, severity, firsteventtime, lasteventtime,
  alarmacktime, alarmackuser, description, logmsg, ifindex, location,
  event_uei, event_severity, event_timestamp, event_node_id, event_log_msg
) VALUES ( … )
ON CONFLICT (reductionkey) DO UPDATE SET
  severity        = EXCLUDED.severity,
  counter         = EXCLUDED.counter,
  lasteventtime   = EXCLUDED.lasteventtime,
  alarmacktime    = EXCLUDED.alarmacktime,
  alarmackuser    = EXCLUDED.alarmackuser,
  description     = EXCLUDED.description,
  logmsg          = EXCLUDED.logmsg,
  ifindex         = EXCLUDED.ifindex,
  ipaddr          = EXCLUDED.ipaddr,
  serviceid       = EXCLUDED.serviceid,
  event_uei       = EXCLUDED.event_uei,
  event_severity  = EXCLUDED.event_severity,
  event_timestamp = EXCLUDED.event_timestamp,
  event_node_id   = EXCLUDED.event_node_id,
  event_log_msg   = EXCLUDED.event_log_msg;
```

`alarmid` is omitted from the INSERT column list — the database sequence
assigns it via `DEFAULT`. The denormalized `event_tsid`, `event_source`,
`last_event_data` columns are not listed; they default to NULL.

Exact column list locked at plan-writing time (some columns above are
horizon-vestigial — `x733*`, `qos*` — and may be omitted from the proto
and the projection).

Notes:

- **Conflict target is `reductionkey`, not `alarmid`.** In `kafka-only`
  mode alarmd does not read or write PG, so it has no PG-assigned
  `alarmid` to put on the wire — every new alarm publishes `alarm_id=0`.
  PG's sequence still generates `alarmid` on INSERT via the column's
  `DEFAULT nextval(...)`; the materializer omits `alarmid` from the
  INSERT column list so the sequence fires for new rows. `alarmid`
  becomes a **private database identifier**, not a public Kafka
  identifier. The Kafka `reduction_key` is the public, durable identity.
  Plan-time pre-work confirms `alarms.reductionkey` has a unique
  constraint (horizon ships it; delta-v's schema inherits it but should
  be verified).
- **Cross-track impact on alerts-forwarder.** Track 2b's `AlarmEnricher`
  currently emits `alarm_id` as a Prometheus label
  (`labels.put("alarm_id", Integer.toString(alarm.getAlarmId()))`). After
  the GA flip to `kafka-only`, that label becomes `"0"` for every new
  alarm — useless as identity, and a label-cardinality footgun if
  operators query by it. **Track 3 includes a Track 2b retrofit** that
  removes `alarm_id` from the enricher's label map (and from any
  consumer-template documentation), leaving `reduction_key` as the
  identity label. The retrofit ships in the same release as the GA flip;
  rcN dual-write still emits real `alarm_id` values for the transitional
  period.
- **Ack/memo columns are included** in the UPDATE clause. They flow
  through the topic (a future workflow REST surface on alarmd publishes
  state changes the same way reductions do), so the materializer
  faithfully projects them. They are *not* "user-owned columns the
  materializer must skip."
- **FK lookups for `nodeid`, `serviceid`** are direct — the proto carries
  `node_id` as an `int32` and `service_name` as a string; the materializer
  resolves `service_name` → `serviceid` via a small in-process cache.
- **`lasteventid` is removed in delta-v's schema** (horizon 36.0.0 changeset
  `36.0.0-drop-alarm-event-fk`, "events move to Kafka"). It is replaced by
  eight denormalized event-shape columns on the `alarms` row:
  `event_tsid`, `event_uei`, `event_source`, `event_severity`,
  `event_timestamp`, `event_node_id`, `event_log_msg`, `last_event_data`.
  All nullable.
- **The materializer populates the overlapping event_* columns from the
  existing proto fields** and leaves the rest NULL in v1.3 Track 3:

  | Column            | Source                                     |
  |---|---|
  | `event_uei`       | `AlarmState.uei`                           |
  | `event_severity`  | `AlarmState.severity` (enum number)        |
  | `event_timestamp` | `AlarmState.last_event_time_ms`            |
  | `event_node_id`   | `AlarmState.node_id` (when > 0)            |
  | `event_log_msg`   | `AlarmState.log_message`                   |
  | `event_tsid`      | NULL — not on the proto                    |
  | `event_source`    | NULL — not on the proto                    |
  | `last_event_data` | NULL — not on the proto                    |

  Documented limitation: anyone reading `event_tsid`, `event_source`, or
  `last_event_data` from `alarms` in kafka-only mode sees NULL. If a
  future consumer (BSMD enrichment, REST API, etc.) needs them, the
  proto can be extended additively at new tag numbers (proto is
  forward-compatible per its own versioning rules) and the materializer's
  projection updated. Tracked as a follow-up; not v1.3 Track 3 work.

### 4.4 Tombstone handling

A tombstone record (null value) on the topic triggers:

```sql
DELETE FROM alarms WHERE reductionkey = ?;
```

The Kafka message key on a tombstone is `reduction_key` — that is the
only identifier the consumer has, which is why the delete is keyed by
`reductionkey` and not `alarmid`. This matches the upsert path (§4.3),
which uses `reductionkey` as its conflict target.

**The consumer is the only PG writer in Track 3.** The retention engine
(§4.5.3) does *not* delete PG rows directly; it only produces
tombstones. This enforces the "Kafka is the source of truth" invariant
at the code level — there is one and only one path from the topic into
PG, and PG mutations always lag a topic event.

Horizon's `KafkaAlarmPublisher.handleDeletedAlarm` callback (from Track
1) remains wired but is dormant in delta-v after Track 3 — no alarmd
code path calls it. It costs nothing and provides forward compatibility
if a future workflow API publishes deletes through alarmd.

### 4.5 Retention rules

Operator-facing YAML in `application.yml` (or an external config map):

```yaml
deltav.alarms-materializer.retention:
  cadence: PT1M                                 # scheduled scan interval
  rules:
    - id: cleared-idle-short
      when:
        severity_at_most: NORMAL
        idle_for: PT5M
        acked: false
        ticketed: false
      action: delete

    - id: long-cleared
      when:
        severity_at_most: NORMAL
        idle_for: P1D
      action: delete

    - id: gc-everything
      when:
        idle_for: P3D
      action: delete

    - id: gc-archived
      when:
        # 'archived' is reserved for a future archive flag; not enforced in v1.3
        archived: true
        idle_for: P8D
      action: delete
```

#### 4.5.1 Predicate fields

| Field | Type | Semantics |
|---|---|---|
| `severity_at_most` | enum (`INDETERMINATE`/`CLEARED`/`NORMAL`/`WARNING`/`MINOR`/`MAJOR`/`CRITICAL`) | Match alarms with severity ≤ value (enum-number compare, same as alerts-forwarder filter) |
| `severity_at_least` | enum | Match alarms with severity ≥ value |
| `idle_for` | ISO 8601 duration | Match when `now() - lasteventtime ≥ value`. "Idle" is defined as no incoming event for the duration — same as horizon's Drools semantic |
| `acked` | bool | `acked: true` matches when `alarmacktime IS NOT NULL`; `false` matches when `alarmacktime IS NULL` |
| `ticketed` | bool | `ticketed: true` matches `tticketstate IS NOT NULL`; `false` matches null |
| `uei_pattern` | regex string | Match alarm UEI against pattern |
| `category_pattern` | regex string | Match any of the alarm's node categories (joined from node-context) against pattern |
| `location` | string (exact) | Match alarm location |

All predicate fields within a single rule are **AND-ed**. Cross-rule OR
is expressed by writing multiple rules. This keeps the surface
schema-validatable and machine-describable for a future MCP-driven
authoring layer ([[project_deltav_mcp_service]]).

#### 4.5.2 Action vocabulary

For v1.3: `action: delete` only. The schema reserves the field so future
actions (`archive`, `annotate`, `set_severity`) can be added in an
additive way. Unknown actions fail startup validation.

#### 4.5.3 Cadence and execution

A single `@Scheduled` task in the materializer, default cadence `PT1M`.
Each scan reads the active alarm set from PG (a single bounded query
selecting `reductionkey` plus the predicate-evaluation columns —
`severity`, `lasteventtime`, `alarmacktime`, `tticketstate`, `uei`,
`location`), evaluates each rule against each row, and for matches
issues:

```java
kafkaProducer.send(topic, reductionKey, null);   // tombstone
```

That is the **only** action retention takes. The materializer's
consumer (§4.4) reads the tombstone and executes the actual PG
`DELETE`. This keeps the "consumer is the only PG writer" invariant
intact and makes the data flow strictly unidirectional:

```
retention scan → tombstone produce → consumer reads → PG DELETE
```

Implications worth noting:

- **Retention is eventually consistent with the scan.** Between the
  tombstone produce and the consumer's delete, the row is still in PG.
  On the next scheduled scan (default 1 minute later) the rule matches
  again and emits another tombstone for the same key. The redundant
  tombstone is benign — the consumer's DELETE is idempotent and
  compaction collapses duplicate tombstones — but it does spend
  Kafka I/O. We accept the redundancy; a "tombstone-emitted-since-last-
  scan" in-memory set is a possible optimisation if scans get large.
- **No risk of the retention task writing PG.** The retention engine
  has no `JdbcTemplate.update("DELETE ...")` call path. Code-level
  enforcement of the invariant.
- **alarmd's `ReductionCache` evicts via the same tombstone** — it
  consumes the topic just like the materializer does. One produce,
  three consumers each react.

The cadence runs on a dedicated executor, separate from the consumer
thread, so retention work never blocks ingest.

#### 4.5.4 Schema validation

`RetentionRulesValidator` runs once at startup against a checked-in JSON
Schema (`src/main/resources/retention-schema.json`). Invalid config
causes the application to fail startup with a clear error pointing at
the offending rule by `id`. No silent rule drift.

## 5. Cutover policy and migration

### 5.1 Default at v1.3.0 GA

`deltav.alarmd.persistence.mode = kafka-only`. The materializer is the
sole writer of the PG `alarms` table.

### 5.2 Escape hatch

`deltav.alarmd.persistence.mode = dual-write` reverts alarmd to Track 1
behaviour (writes PG + publishes Kafka). Available throughout v1.3.0,
removed in the release after v1.3.0 GA.

### 5.3 Supported upgrade path

| From | To | Path |
|---|---|---|
| v1.3.0-rcN (dual-write running) | v1.3.0 GA (kafka-only) | **Hot cutover.** Materializer starts, replays compacted topic, projects to PG (idempotent — no net change since PG and topic are already consistent from dual-write). Operator deploys new alarmd image with `persistence.mode=kafka-only`. |
| v1.2.x | v1.3.0 GA | **Stage through rcN.** Documented as "go v1.2.x → v1.3.0-rcN dual-write → v1.3.0 GA." Direct upgrade is unsupported in v1.3.0. |

### 5.4 Why direct v1.2.x → Track 3 is not supported

A pre-v1.3.0 deployment has PG alarms but an empty topic. If alarmd
started in `kafka-only` mode, the `ReductionCache` bootstrap-replay would
finish with an empty cache, every incoming event would look new (no
reduction), and the existing PG rows would become orphans (materializer
projects an empty topic into a non-empty PG). The complications of a
one-shot PG → topic backfill (run-once guard, replayability,
ordering-with-incoming-events) outweigh the value for what is effectively
a staging step the operator can take in any case.

### 5.5 Pre-GA tabletop

Before flipping the default to `kafka-only` in GA, the parent spec
requires a **failure-mode tabletop**: walk the failure cases (Kafka
outage during steady state, materializer crash, materializer falls behind
by N minutes, alarmd crashes mid-publish, topic replay produces an
unexpected upsert) and confirm the design is correct end-to-end. The
tabletop is a deliverable of Track 3, not optional.

## 6. Failure modes

| Failure | Behaviour | Recovery |
|---|---|---|
| Kafka broker outage | Alarmd stops consuming `deltav-fault-events` and stops producing to `deltav-alarms-state-change`. Events back up on the input topic; Minions buffer upstream (existing behaviour). Materializer stops consuming; PG state is frozen. | Automatic on broker recovery — both consumers resume. |
| Alarmd cold start while broker is down | `ReductionCache` bootstrap-replay stalls. `/actuator/health` stays not-ready until broker is reachable. K8s would not route traffic. | Automatic. |
| Materializer crash | Topic continues accumulating records; PG falls behind. Other consumers (alerts-forwarder, BSMD via PG) keep functioning at their own consistency. | On restart, bootstrap-replay catches PG up. Idempotent upserts mean replay is safe regardless of how far behind it fell. |
| Materializer is slow (replay during steady state) | PG lag grows. BSMD and any PG-reader see stale data with bounded staleness. | Natural — lag closes when the materializer catches up. Monitored via `deltav_alarms_materializer_consumer_lag_records`. |
| Materializer SQL error (DB unreachable, constraint violation) | Consumer thread blocks retrying. Natural back-pressure — broker keeps the record, no data loss. | Automatic on DB recovery; consumer resumes. |
| Alarmd crashes after `producer.send` but before consumer-side cache update | The record is on the topic; on restart, bootstrap-replay re-reads it and the cache is consistent. | Automatic. |
| Tombstone published but materializer hasn't processed it | PG has a row that should be deleted. Eventually consistent — materializer catches up and deletes. If retention scan re-fires before the consumer catches up, it emits a redundant tombstone; benign — duplicate tombstones collapse on compaction, the DELETE is idempotent. | Automatic. |
| Tombstone races with a re-publish (alarm deleted then re-created) | If alarmd publishes `state` after `null` for the same key, the materializer upserts again — the alarm is re-created with a fresh PG-sequence-generated `alarmid`. Honest semantics: the topic is the SOT and the last write wins. Consumers identify the alarm by `reduction_key`, so the new `alarmid` is invisible to them. | n/a (correct behaviour). |
| Topic compaction occurs while alarmd is restarting | The compacted topic still contains the latest record per key, so cache bootstrap is correct. Tombstones may have been compacted away (Kafka eventually removes tombstones after `delete.retention.ms`) — this is fine for cache bootstrap (a missing key just means no active alarm). | Automatic. |

## 7. Read-path consistency

After Track 3, all PG `alarms` readers (BSMD, future REST surface, future
UI) see an eventually-consistent view of alarm state. Targets:

- **Steady-state lag SLO:** materializer lag ≤ 1s at p99 under normal
  load (Track 1's smoke run showed ~7 records per import; load is light).
  Spike tolerance: ≤ 10s p99 during a burst of 1000 events/min.
- **Cold-start replay budget:** for a topic with 10,000 active alarms,
  full bootstrap (alarmd `ReductionCache` + materializer first pass)
  completes within 30s on the smoke VM. Larger deployments scale
  proportionally.
- **BSMD impact:** BSMD consumes alarms via `AlarmDao` and correlates
  into business-service state. After Track 3, BSMD sees the same view as
  any other PG reader. The materializer lag becomes BSMD's correlation
  lag. Document as a known property; no BSMD-side change in v1.3.

These targets are smoke-environment baselines, not contractual SLOs.
Re-validate during the failure-mode tabletop.

## 8. Testing strategy

JUnit 5 Jupiter only ([[feedback_boot4_junit_platform_launcher]]).

### 8.1 Unit tests

- `ReductionCache` — bootstrap completion event, tombstone evicts, get-by-rk.
- `DeltavAlarmPersister` — mode switching (kafka-only vs dual-write),
  reduction lookup hits ReductionCache instead of `AlarmDao`.
- `AlarmStateProjector` — proto → SQL parameter row mapping.
- `AlarmUpsertWriter` — `INSERT … ON CONFLICT` clause shape (via
  `JdbcTemplate` mocks).
- `PredicateEvaluator` — all predicate fields exercised individually
  (severity, idle, acked, ticketed, uei_pattern, category_pattern,
  location). AND composition. Schema validation rejects unknown actions.
- `RetentionRulesValidator` — known-bad YAML fails fast with the rule id
  in the error.

### 8.2 Integration tests

- Testcontainers Kafka + PostgreSQL: publish synthetic `AlarmState`
  records to a test topic; assert the materializer's PG row matches.
- Idempotency: re-publish a record; assert PG state unchanged.
- Tombstone: publish a tombstone for an existing key; assert `DELETE FROM
  alarms WHERE reductionkey = ?` executes; PG row is gone.
- Retention: seed PG with rows matching/non-matching a rule; trigger the
  scan task; assert the right rows are deleted and tombstones are
  produced.
- Bootstrap-replay correctness: stop and restart the materializer
  mid-stream; assert no records are lost and no rows are stale.
- Alarmd cold-start: start alarmd with a pre-populated topic; assert the
  `ReductionCacheReadyEvent` fires and the first event reduction uses
  the cached state.

### 8.3 E2E smoke (existing harness)

The implementation-agnostic `test-alarm-cleanup-e2e.sh` pattern saved
from the Drools session ([[project_alarmd_state_management_strategy_open]])
covers the retention path end-to-end: fire a `linkDown` trap →
assert PG row created → fire `linkUp` → assert severity → wait the
configured idle window → assert PG row deleted AND tombstone visible on
the topic AND alarmd `ReductionCache` size decremented.

## 9. Future-friendliness for follow-ups

These are explicitly *not* Track 3 deliverables but the design must not
foreclose them.

| Follow-up | What Track 3 must not break |
|---|---|
| **Workflow REST API (ack/memo/escalate)** | Ack/memo columns flow through the topic; the materializer projects them. A future REST handler on alarmd publishes the same `AlarmState` records after applying user input. No special "workflow producer" surface needed. |
| **Drools (or other) rules engine sidecar** | The topic is the input. The sidecar consumes `deltav-alarms-state-change` and produces commands to a future `deltav-alarm-commands` topic that alarmd or the materializer consumes. Boot 4 colocation issue ([[project_alarmd_alarm_lifecycle_gap]]) is sidestepped because the sidecar is its own JVM. |
| **Alertmanager auto-silence on ack** | The alerts-forwarder gains a silence-API client that watches for `ack_user`/`ack_time_ms` populated on `AlarmState` and POSTs a matching silence to Alertmanager. No change to the topic, the materializer, or alarmd. |
| **MCP-driven rule authoring** | The retention rule YAML schema is JSON-Schema-validated with named fields and stable rule IDs ([[project_deltav_mcp_service]]). An MCP layer can compose rules without ambiguity. |
| **Retire PG alarms entirely (Phase 3)** | Other PG readers (BSMD) move to consume the topic directly; the materializer becomes a no-op and is removed. Track 3's architecture imposes no obstacle. |

## 10. Deliverables

- **`core/alarms-materializer` module** — pom, Dockerfile, application.yml,
  Spring Boot 4 entry point.
- **Consumer** — `AlarmStateKafkaConsumer` (cloned from alerts-forwarder).
- **Upsert writer** — `AlarmStateProjector`, `AlarmUpsertWriter`. SQL uses
  `ON CONFLICT (reductionkey)`; `alarmid` is omitted from the INSERT
  column list and filled by PG's sequence.
- **Deleter** — `AlarmDeleter` (handles topic tombstone reception via
  `DELETE FROM alarms WHERE reductionkey = ?`).
- **Retention engine** — `RetentionEngine`, `PredicateEvaluator`,
  `RetentionRulesValidator`, `retention-schema.json`. Produces tombstones
  only; does not delete PG rows directly.
- **Metrics constants** — `MaterializerMetrics`.
- **Alarmd changes:**
  - `ReductionCache` + `ReductionCacheKafkaBootstrap` + `ReductionCacheReadyEvent`.
  - `DeltavAlarmPersister` replaces `AlarmPersisterImpl` as the
    `alarmPersister` bean in `AlarmdConfiguration`.
  - `deltav.alarmd.persistence.mode` config property.
- **Track 1 publisher retrofit:** `KafkaAlarmPublisher` `producer.send`
  moves to a `TransactionSynchronization` AFTER_COMMIT callback (with
  `fallbackExecution = true`), so it cannot race alarmd's open
  transaction in `dual-write` mode. Applies in both modes for path
  uniformity. See §3.2.1.
- **Track 2b alerts-forwarder retrofit:** remove the `alarm_id` label
  from `AlarmEnricher`'s label map (and from any consumer-template
  documentation that copied it). Reduction key is the durable identity
  after Track 3; `alarm_id` is `0` for every new alarm in `kafka-only`
  mode and must not be presented as identity. Ships alongside the GA
  flip.
- **Compose / build wiring** — `docker-compose.yml`, `build.sh`,
  `.github/workflows/delta-v-build-images.yml`, `.env.example`.
- **Tests** — unit + integration coverage per §8; reused
  `test-alarm-cleanup-e2e.sh` for retention.
- **Tabletop document** — pre-GA failure-mode tabletop write-up. Path is
  to be decided when the tabletop is run (the `docs/superpowers/tabletops/`
  directory does not yet exist; the plan step that runs the tabletop
  creates it).
- **Grafana dashboard panels** — materializer lag + retention work added
  to the existing "Alerts Pipeline" dashboard. Deferred to a follow-up
  PR after the daemon is live.

## 11. Risks

| Risk | Mitigation |
|---|---|
| **`AlarmPersisterImpl` is a horizon class with non-obvious internal contracts.** Subclassing it for mode-switching may surface protected state we don't see in the Track 1 code path. | Resolve in plan-writing: read `AlarmPersisterImpl.persist()` and any helper methods carefully. If subclassing is unstable, the fallback is to replace the bean entirely with a delta-v implementation of the `AlarmPersister` interface. |
| **Event-topic partitioning may not be by reduction-key-relevant fields.** Per-rk serialisation depends on same-rk events landing on the same partition. | Pre-work: confirm `deltav-fault-events` partitioning. If not compatible, add a small in-process per-rk striped lock in alarmd (cheap, well-understood). |
| **PG `alarms.lasteventid` column** — horizon FK to events, delta-v has no events table. Either the column is nullable or removed. | Pre-work in plan-writing: read delta-v's schema migration history; adjust the proto / projection if needed. |
| **`alarms.reductionkey` unique constraint must exist** for `ON CONFLICT (reductionkey)` to be the correct upsert target. | Pre-work: verify the constraint in delta-v's schema (horizon ships it as `alarms_reductionkey_idx UNIQUE`). If missing, add a Liquibase migration to introduce it before the materializer ships. |
| **Track 1 publisher transactional ordering is not currently AFTER_COMMIT.** Today's `KafkaAlarmPublisher.handleNewOrUpdatedAlarm` fires synchronously inside the `AlarmPersisterImpl` transaction. Cutting over without §3.2.1 would race the materializer against alarmd's open transaction. | The §3.2.1 retrofit lands **before** the materializer is enabled in any deployment. Order matters in the PR series. |
| **`alarm_id` label leakage in alerts-forwarder** — Track 2b's `AlarmEnricher` exposes `alarm_id` as a Prometheus label. After GA it is `0` for every new alarm. | Retrofit ships in the same release as the GA flip (§10 deliverables). Confirm by smoke before the default flip. |
| **BSMD lag visibility.** Operators may not notice that BSMD is now eventually consistent. | Document. Add a dashboard panel for materializer lag. Optional v1.3 follow-up: a "stale read" warning header in BSMD's REST output when lag > threshold. |
| **Bootstrap-replay on alarmd cold start adds startup time proportional to active alarm count.** | Smoke-baseline for representative scale. Add `deltav_alarmd_reduction_cache_bootstrap_seconds` so operators can plan around it. |
| **alarmd-startup regressions remain CI-invisible** — same risk family that caused the Drools revert. | Mandatory: every Track 3-affecting PR carries a local docker-compose "boot alarmd in kafka-only mode" confirmation in its body before merge. Maven build + CI green is not sufficient. |
